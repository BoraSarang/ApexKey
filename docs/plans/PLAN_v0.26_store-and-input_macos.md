## T-175 — blob 잠금에 복구 경로

`corruptedShortcutBlobColumns`의 해제 지점이 `load()`·`removeShortcut`뿐이었다.
한 번 디코딩이 실패하면 **영구 쓰기 잠금**이고 복구 방법은 "동작 삭제"뿐.
데이터는 안 사라지지만 **편집이 반영되지 않는다** — 사용자는 버그로 느낀다.

### 설계: 해제 조건 3개 (모두 만족해야 한다)

1. 인코딩 성공 2. 왕복 성공 3. **손상 시점 fallback과 다름**

**3번이 핵심이고, 처음엔 필요 없다고 생각했다.** 1·2(왕복)만으로 충분하다고
생각했는데 틀렸다 — fallback인 `[]`도 인코딩 후 디코딩하면 그대로 `[]`이 돌아온다.
왕복에 성공하므로, 왕복만 보는 가드는 **"손상 원본을 조용히 덮어쓴다"**(P0-3이
막으려던 것)를 **막지 못한다.** 테스트가 이 결함을 실제로 잡아냈다.

값의 **출처**를 추적해야 구별할 수 있다 → `corruptedBlobFallbackBytes`가 손상
시점의 fallback을 기록하고, 저장 시점에 현재 값과 비교한다.

컬럼은 **독립적**이다. steps만 편집하고 triggers는 그대로면 triggers는 유지된다.
"옆 컬럼이 풀렸으니 이건 자동으로 풀리겠지"라는 가정으로 전체를 풀면 손상 원본이
사라진다. 별도 테스트로 고정했다.

**알려진 한계(의도적)**: 사용자가 의도적으로 fallback과 같은 값(빈 배열 등)을 만들면
잠금이 유지된다. 안전 쪽으로 실패하는 선택. 강제 해제 경로는 **두지 않는다** —
원본을 지우는 유일한 방법이 되어 P0-3이 무의미해진다.

## T-177 — `JSONEncoder` 키 순서 결정성 ★ 가장 중요한 발견

T-175의 복구 가드가 **바이트를 비교**하게 되면서 드러난 잠재 결함이다.

`testFallbackValueDoesNotReleaseTheLock`가 **고립 실행에서는 통과하고 전체 스위트에서만
간헐 실패**했다. 진단 테스트를 추가해 좁힌 결과: 같은 `ShortcutPermissions`를 두 번
인코딩하면 **165바이트로 길이는 같은데 내용이 달랐다.**

원인: `JSONEncoder`는 기본(`outputFormatting` 미지정)에서 내부 딕셔너리를 거치는데,
**Swift의 `Hasher` 시드는 프로세스마다 무작위**라 같은 값도 프로세스를 넘기면 키
순서가 달라진다.

`StoreCoding`을 `.sortedKeys`로 고정했다. 이전 데이터는 키로 디코딩하므로 **전부
그대로 읽힌다** — 저장 형식이 깨지지 않는다. 부수적으로 blob이 결정적이 되어
diff·해시 비교가 가능해졌다.

**이게 고쳐지지 않았으면 복구 가드가 간헐적으로 열려 사용자 원본 데이터가 조용히
덮어써질 뻔했다.** 5회 연속 전체 스위트 실행으로 비결정성 제거를 확인했다.

> 교훈: **비결정적 결함의 전형적 징후는 "고립 실행은 통과하고 전체 스위트에서만
> 실패"다.** 같은 증상이 보이면 원인을 재현 데이터로 좁힐 것. 추측하지 말 것.

## T-176 — 저장 debounce

`onChange(of: steps)` → `syncShortcut` → **blob 4컬럼 재인코딩 + save**가 매 편집마다
발생. 드래그 재배열이나 한 글자씩 지우면 그만큼 저장되고 중간 상태가 디스크에 남는다.

**무엇을 합치고 무엇을 합치지 않는가 — 이게 설계의 요점**

| 합친다 | 합치지 않는다 | 이유 |
|---|---|---|
| `updateShortcutSteps` (연속 호출 → 마지막 값) | 추가·삭제·복제·이름 변경 | 명시적 동작을 합치면 "추제한 게 잠깐 안 보인다"는 불안이 생긴다 |

**빈도가 다른 두 경로를 구분한 것**이 핵심이다. debounce는 본질적으로 저장을
**늦춘다** 그래서 유실 방지가 더 중요하다:
- `flushNow()` — 창·앱 종료
- `applicationWillTerminate`에서 `store?.flushPendingSaves()`
- 실행 순서 보존 (나중 예약이 나중 실행 — 뒤집히면 옛 값이 이긴다)

**스레드 안전**: `queue.sync`를 쓰지 않았다. 상태 접근에 `queue.sync`를 쓰면 같은 큐에서
호출할 때 즉시 데드락한다 — 테스트가 `@MainActor`이고 기본 큐가 `.main`이라 반드시 만난다.
`NSLock`으로 상태를 보호하고 실행만 큐 위에서 한다.

## T-179 — 키 입력 3종

### 게시와 계획을 분리

`TypingActions.plan(_:)`은 순수 함수다 — "무엇을 보낼지"만 계산하고 권한·포커스와
무관하다. 왜 이 분리가 필요한가: 키 입력은 `AXIsProcessTrusted()`가 없으면
**조용히 무응답**이 된다. 그 상태를 그대로 테스트하면 "보냈지만 아무 일도 안 일어난"
성공처럼 보인다.

- **한글을 절대 자르지 않는다.** `CGEventKeyboardSetUnicodeString`은 버퍼 한도가 있어
  조각이 필요한데, **Character 경계**에서만 자른다. UTF-16 단위로 자르면 결합 한글이
  깨진다. `maxUnitsPerEvent = 20`은 한글 조합형이 2~3 유닛을 쓰는 점을 감안한 값
- **숫자가 아니면 실패다.** 조용히 0으로 바꾸면 "입력했는데 반영이 안 되지"가 남는다

### HTML→Markdown: Foundation 대신 자체 파서

`NSAttributedString` HTML 임포트는 WebKit에 의존하고 샌드박스 밖 파일 접근과 스크립트
실행을 시도한다. 런처가 매 실행마다 그 경로를 타는 것은 과하다. 대상이 정적
프래그먼트(이메일 본문 등)라 작은 파서로 충분하다.

- **조용히 통과시키지 않는다** — 태그가 하나도 없으면 `noHTMLContent`로 실패
- 닫히지 않은 태그는 **자동 닫힘** (브라우저와 같다). 불균형을 실패로 만들면
  이메일 조각 하나에 전체 변환이 실패한다
- **알 수 없는 태그의 내용은 보존한다** — 통째로 버리면 데이터 손실
- `script`·`style`·`head`는 내용까지 버린다 — 본문 오염 방지

### 테스트가 잡은 실제 버그 3건

1. 엔티티 디코딩이 `&amp;` → `&;` (닫는 `;` 잔존)
2. 링크 href가 `[링크](Optional("https://…"))` (Optional 보간)
3. 닫는 태그만 있는 입력(`텍스트</div>`)이 "HTML 아님"으로 오판

## T-181 — Run Shortcut 전용 설정 UI

백로그에 "조회 단계 연결"로 남아 있었는데 조사 결과 **엔진은 정상이었고 설정 UI가
없었다.** `executeRunShortcut`는 `step.target`에 UUID를 받는데 `StepSettingsView`에
case가 없어 `DefaultSettingsView`(자유 입력 필드)로 떨어졌다 — 사용자가 UUID를 직접
찾아 입력해야 했다. "엔진은 되는데 아무도 못 쓰는" 상태.

- 동작 피커(이름순) + 대상 단계 미리보기
- **자기 자신은 후보에서 제외** — 재귀 호출이 되고 사용자는 depth 제한 이유를 모른다
- **대상이 삭제되면 경고** — 조용히 빈 값으로 보이면 안 된다

### ★ `@EnvironmentObject` 주입 누락 — 크래시 확정

`RunShortcutSettingsView`는 동작 목록을 읽으므로 store가 필요한데, 이 창은
`ThemedRoot`로 호스팅되고 **`ThemedRoot`는 theme만 주입한다.** 주입하지 않으면
`@EnvironmentObject` 접근 시 **런타임 크래시**가 난다(빌드는 통과한다).
`showStepSettings`에서 `.environmentObject(store)`를 넣고, store 미초기화 시
창을 열지 않고 로그만 남기도록 했다.
