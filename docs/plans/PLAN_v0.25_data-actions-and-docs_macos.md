## T-172 — 수치·날짜·목록 액션 12종

`changeCase`·`sort`·`surroundText`·`wordCount`·`calculate`·`math`·`number`·
`outputDifference`·`base64Encode`·`hash`·`uuid`·`dateFormatter`.

### 왜 이 12종인가

미구현은 103종이 남았다. 대부분(`Photos`·`Music`·`Mail`·`Calendar`·`Reminders`·
`Podcasts`)은 Apple 앱 연동이라 ScriptingBridge나 URL scheme이 필요한데,
**각 앱의 API를 조사하지 않고 구현을 시작하면 되돌아올 수 없다.**
순수 로직으로 완결할 수 있는 것부터 처리하는 편이 낫다고 판단했다.

### 설계 판단 4가지

**1. 계산기는 `eval`을 쓰지 않는다.**
`NSExpression`은 기본 비활성이고, 활성화해도 임의 코드 실행 위험이 있다.
재귀 하강 파서를 직접 구현했다 — 우선순위(`^` > 단항 `-` > `* / %` > `+ -`),
오른쪽 결합 거듭제곱(`2^3^2 = 512`), 괄호, 단항 마이너스, `×÷−` 수학 기호,
지수 표기, 재귀 깊이 64 제한.

**2. 0으로 나누기는 명시적 실패다.**
IEEE 754는 `inf`를 반환한다. 그건 오류가 아니라 조용히 이상한 값이라서,
사용자는 "결과가 이상하다"를 알 수 없다. 같은 이유로 `0.1+0.2`의 부동소수점
노이즈는 정리해 준다.

**3. 정렬에서 숫자가 아닌 항목은 뒤로 보낸다.**
0으로 취급하면 "앨범"이 숫자 0으로 정렬되어 순서가 거짓말이 된다.

**4. MD5를 넣지 않았다.**
MD5는 충돌이 실제로 만들어지는 해시다. "해시"라는 이름 아래 제공하면
위험한 primitive를 제공하는 셈이다. CryptoKit의 SHA-256/512만 노출한다.

### 테스트가 잡은 실제 버그 2건

이 커밋 이전 상태에서:

1. **괄호 중첩 깊이 제한이 동작하지 않았다.** `parsePrimary`가 괄호 안에서
   `parse()`를 depth 기본값 0으로 호출해 리셋했다. `((((...))))` 500중첩이
   제한을 끝내 통과했다. → `parsePrimary(depth:)`로 깊이를 threading
2. **회귀 테스트의 기대값 오류.** "공백   많음"을 3단어로 기대했는데 2단어다
   (코드가 맞고 테스트가 틀렸다)

1번은 "깊은 입력에서 스택을 터뜨리지 않는다"는 보장이 실제로 성립하지 않았다는
뜻이다. 테스트가 없었다면 그대로 배포됐다.
