> 질문: "두 손가락 에지 볼륨 조절이 왜 이렇게 어렵나. 내가 너무 어려운 기능을 넣으려 한 건가, 이 앱이 이상한 건가."
> 범위: macOS 내장 제스처 + 서드파티 제스처·에지 슬라이더 앱 6종 + 현재 ApexKey 구현 대조. **코드 변경 없음.**

## 0. 결론 먼저

**넣으려 한 기능이 이상한 게 아니다.** 가장자리 슬라이더는 이미 시장이 있는 기능이고, 같은 일을 하는 앱이 최소 6개(ApexKey 포함 7개)다. 2026년에도 새 앱이 계속 나온다.

**문제는 개념이 아니라 상호작용 설계다.** 이 카테고리에서 살아남은 앱들은 예외 없이 같은 결정을 한다. ApexKey의 기본값은 그 결정과 **정면으로 반대**다.

| 항목 | 업계 수렴값 (전용 앱 6종) | ApexKey 기본값 | 판정 |
|---|---|---|---|
| 손가락 수 | **1개 기본** (Ledge만 1·2 허용) | 2개 | ✗ macOS와 충돌 |
| 에지 판정 | **에지 띠 + 즉시 시작**, 일부는 패드 밖 **진입 궤적** 요구 | 정지 위치 띠(15%) | ✗ 손을 갖다 대야 함 |
| 값 매핑 | **연속**(이동 = 값, 전 구간) | 이산(14% 이동당 1/16) | ✗ 0→100%에 2.2회 스와이프 |
| 시작 임계값 | **약 1mm** | 트랙패드 높이의 7% | ✗ 시작 전 스크롤 발생 |
| 햅틱 | **스텝마다 틱** | 없음 | ✗ "슬라이더 감각"의 핵심 |
| 스크롤 억제 | 슬라이드 시작 **전** | 활성화 **후** | ✗ 첫 7%에서 페이지가 움직임 |

즉 **"어려운 기능을 무리해서 넣었다"기보다, 이미 검증된 기능을 검증되지 않은 방식으로 구현했다.** 재설계 비용은 크지 않다(엔진·HUD·스크롤 억제·권한 체계는 그대로 재사용).

## 1. 현재 구현 실측값 (코드가 출처)

`Sources/ApexKey/Trackpad/` 기준. 문서가 아니라 코드에서 읽은 값이다.

| 파라미터 | 값 | 위치 | 체감 영향 |
|---|---|---|---|
| 기본 손가락 | **2** | `TrackpadModels.swift` `fingers: Int = 2` | 2손가락 세로 = macOS 스크롤 |
| 기본 에지 | 오른쪽 | `edge: TrackpadEdge = .right` | 2손가락 + 오른쪽 = macOS 알림 센터 |
| 에지 띠 폭 | 0.15 (패드 폭의 15% ≈ 2.4cm) | `edgeWidth` | 정지 위치로 판정 → 손을 갖다 대야 함 |
| 손가락 벌어짐 허용 | 0.10 | `fingerSpread` | 띠 밖 손가락 허용 |
| 시작 임계값 | 0.07 (높이의 7% ≈ 0.7cm) | `startThreshold` | 이때까지 스크롤이 살아 있음 |
| 스텝 거리 | 0.14 (14%) | `stepDistance` | 0→100%에 **224% 이동 ≈ 2.2회 풀 스와이프** |
| 스텝 값 | 1/16 (6.25%) | `stepValue` | 키보드 볼륨키 1회와 동일 |
| 쿨다운 | 0.12초 | `cooldown` | 초당 최대 8.3스텝 → 풀 구간 최소 1.9초 |
| 잔여 누적 상한 | 2스텝 | `maxResidualSteps` | 빠른 스와이프 입력 유실 |
| 엄지 무시 | 하단 15% | `thumbZone` | 접촉 **크기**가 아닌 위치 기준 |
| 스크롤 억제 시점 | `.activated` 이후 | `TrackpadEngine.swift:192` | 시작 7% 구간은 페이지가 스크롤됨 |
| 햅틱 | 없음 | — | — |
| 포인터 고정 | 없음 | — | 슬라이드 중 커서 이동 |
| 타이핑 가드 | 없음(쿨다운 120ms만) | — | 타이핑 중 오작동 |

**BTT의 자기 문서 예제가 볼륨을 "3손가락 연속 세로 스와이프"로 든다.** 2손가락을 쓰지 않는다. 이유는 명시하지 않지만, 2손가락 세로가 스크롤이라는 사실과 무관하지 않다. 반면 에지 슬라이드는 1손가락·2손가락 모두 제공하고, 6.997에서 **손바닥 오인식(palm rejection)을 대폭 개선**했다고 밝힌다.

**수렴점 6개** — 서로 코드도 라이선스도 다른 앱들이 독립적으로 같은 답에 도달했다:

1. **1손가락** (예외: Ledge는 2손가락도 허용하지만 기본은 1)
2. **정지 위치가 아니라 진입 궤적**으로 에지를 판정 (Margin·Fringe가 명시)
3. **연속 매핑** — 손가락 이동 = 값 이동, 전 구간이 한 번의 슬라이드
4. **슬라이드 중 스크롤·포인터 고정**
5. **접촉 크기 기반 팜 리젝트 + 타이핑 가드**
6. **햅틱 틱** — "진짜 슬라이더" 감각의 핵심

### 2-D. 스크롤 유틸 (참고)

Mos·LinearMouse·Scroll Reverser는 스크롤 감도·가속·방향을 고치는 별도 카테고리다. 에지 슬라이더와 경쟁하지 않고, **"2손가락 세로 = 스크롤"이라는 사용자 학습을 더 강하게 고정**시킨다.

## 3. 사용자 불만 3건의 원인

### 3-1. "감도가 안 맞는다"

숫자로 설명된다.

- 기본값에서 볼륨 0→100%는 **16스텝 × 14% = 트랙패드 높이의 224%** 이동이다. 16인치 MacBook Pro 트랙패드 높이 약 10cm 기준 **약 22cm**, 즉 **풀 스와이프 2.2회**.
- 각 스텝은 `cooldown 0.12s`로 게이트되므로 아무리 빨리 움직여도 **최소 1.9초**.
- 빠른 스와이프는 `maxResidualSteps 2`에서 잘려 **입력이 버려진다.**

대조: Ledge는 **전 구간 = 1회 슬라이드**, 1% 스텝에 민감도 기본 1.5×. BTT도 "Movement for the full range"로 같은 모델을 쓴다.

→ 사용자가 감도를 2.0으로 올려도 **스텝 모델 자체가 병목**이라 해결되지 않는다. 실제로 v0.33.1에서 12%→14%로 **더 둔하게** 조정한 이력이 있다(예민하다는 피드백의 반대편).

### 3-2. "두 손가락을 에지에 맞추기 어렵다"

세 가지가 겹친다.

1. **정지 위치 판정** — 손가락이 이미 에지 띠 안에 있어야 추적이 시작된다. 전용 앱들은 반대로 **패드 밖에서 들어오는 궤적**을 본다(Margin: "패드 안에서 처음 닿은 손가락은 절대 트리거하지 않음"). 후자는 손을 갖다 대지 않고 **쓸어 들어오면** 되므로 위치 정확도 요구가 사라진다.
2. **두 손가락** — 손가락 두 개를 나란히 에지에 붙이면 폭이 3~4cm다. 띠 15%(≈2.4cm)보다 넓어서 `spread 0.10` 허용이 필요했고, 코드 주석에도 "전부 띠 안을 요구하면 두 손가락 규칙은 사실상 쓸 수 없다(실기 피드백)"고 적혀 있다. **이미 설계 결함을 인정한 주석이다.**
3. **macOS 알림 센터와 같은 조합** — 오른쪽 에지 + 2손가락은 OS가 이미 쓰는 입력이다. 방향만 다르다. OS와 ApexKey가 같은 프레임을 동시에 보고, 축 판정은 몇 프레임 뒤에나 확정된다.

### 3-3. "위/아래 방향이 헷갈린다"

- 사용자는 **2손가락 세로 = 스크롤**로 훈련돼 있다. 자연 스크롤에서 두 손가락을 위로 밀면 **콘텐츠가 위로 올라간다**(보이는 것은 아래로). 반면 에지 슬라이더의 위 = **값 증가**. 같은 손동작에 반대 의미가 붙는다.
- 1손가락 에지 슬라이드는 이 학습과 충돌하지 않는다. 2손가락은 충돌한다.
- ApexKey에는 `inverted` 옵션이 있지만, **기본값이 틀렸다는 사실을 사용자가 설정에서 발견해야 한다**는 것이 문제다.

### 3-4. 추가: 시작 7% 구간에서 페이지가 움직인다

스크롤 억제는 `.activated` 이후에만 켜진다(`TrackpadEngine.swift:192`). 즉 **슬라이더가 켜지기 전 0.7cm 구간은 스크롤이 그대로 전달된다.** 사용자 입장에서는 "볼륨을 올리려 했는데 페이지가 살짝 내려갔다"로 관측되고, 이것이 "방향이 헷갈린다"는 체감을 증폭시킨다. 전용 앱들은 슬라이드로 판정되는 순간 페이지를 고정한다.

## 4. "이 앱이 이상한가?" — 판정

| 질문 | 답 |
|---|---|
| 기능 자체가 무리인가? | **아니다.** 전용 앱 6종 + BTT가 같은 기능을 출시·유지 중. 2026년에도 신규 진입이 있다 |
| 사용자가 너무 어려운 걸 요구했나? | **아니다.** "에지를 문지르면 볼륨"은 이 카테고리의 표준 UX다 |
| ApexKey 구현이 이상한가? | **기본값이 비수렴하다.** 6개 앱이 모두 피한 조합(2손가락 + 정지 위치 + 이산 스텝)을 기본값으로 골랐다 |
| 실패 원인이 사용자에게 있나? | **없다.** 감도·방향·위치를 사용자가 설정으로 보정하게 만든 것이 설계 부채다 |

한 가지 냉정한 사실: **이 카테고리는 무료 앱이 이미 많다.** Ledge·Fringe·Margin은 오픈소스 무료, Slidr는 $4.99, BTT는 이미 설치된 사용자가 많다. ApexKey가 같은 기능을 "조금 더 나은 수준"으로 유지하는 것의 제품 차별화 이득은 작다. 반대로 **"ApexKey 하나로 키보드·메뉴·트랙패드를 다 한다"**는 통합 이득은 있다.

| 2 | **탭·앱 전환** (3손가락 스와이프 → Ctrl+Tab 등) | BTT, Multitouch | "제스처로 키보드 안 누르기"의 최대 용도 |
| 3 | **중클릭** | Middle | 단일 기능 앱이 성립할 정도 |
| 4 | **스크롤 감도·방향 교정** | Mos, LinearMouse | 2손가락 스크롤 학습을 강화 |
| 5 | **Mission Control·스페이스 매핑** | macOS 내장 + BTT | 내장 대체·보강 |
| 6 | **에지 슬라이더(볼륨·밝기)** | Ledge, Slidr, Fringe, Margin, BTT Fluid | **니치지만 충성도 높음.** "키보드에서 손 안 떼기" |
| 7 | **제스처 → 임의 액션** | BTT, Multitouch, ApexKey | ApexKey의 기존 강점과 겹침 |

시사점:
- 에지 슬라이더는 **상위 3개**가 아니라 **6~7위**다(이 표 기준 추정). "대중적 기능"은 아니지만 **명확한 코어 사용자층**이 있다.
- ApexKey의 정체성(키보드·메뉴 실행)과 가장 잘 맞는 것은 **2번·7번**이다. 트랙패드 제스처→액션은 이미 구현돼 있고, 에지 슬라이더는 그 위에 얹힌 별개 축이다.

## 6. 선택지

### A. 재설계 — 인식기만 교체 (권장)

유지: `MultitouchSource`·`ScrollSuppressor`·`TrackpadHUD`·`GestureRouter`·권한·경계 검사·설정 저장.
교체: `EdgeSliderRecognizer` + 기본 규칙 + 편집 UI 일부.

| 변경 | 내용 |
|---|---|
| 손가락 | 기본 **1개**. 2개는 "고급"으로 남기되 기본에서 제외 |
| 에지 판정 | 정지 위치 띠 → **진입 궤적**(패드 밖/모서리에서 들어와 에지 띠에 닿은 접촉) + 히스테리시스 |
| 시작 임계값 | 0.07 → **약 0.01~0.02**(1~2mm) |
| 값 매핑 | 14%당 1/16 → **전 구간 연속**(이동량 비례), 선택적 스텝 모드 |
| 스크롤 억제 | **추적 시작 즉시** 켜고, 취소 시 해제 |
| 팜 리젝트 | 위치 → **접촉 크기** 기반. 원시 구조체 offset 48에 `size`, 60/64에 major/minor 축, 92에 압력이 있지만 현재 `TrackpadTouch`는 x/y만 노출 — **필드 1개 추가 필요** |
| 햅틱 | `NSHapticFeedbackManager` 스텝 틱 |
| 포인터 | 슬라이드 중 숨김·고정, 종료 시 복원 |
| 타이핑 가드 | 키 입력 후 짧은 구간 신규 접촉 무시 |
| 기본 에지 | 오른쪽 유지. **1손가락이면 알림 센터(2손가락)와 충돌하지 않으므로** 구간 제한은 선택 사항 — 팜 오작동 방지를 위해 하단 일부만 제한 |

비용: 인식기 재작성 + 테스트 갱신. 기존 단위 테스트가 순수 구조체라 이식 가능. **1~2일 규모.**
위험: 비공개 프레임워크 접촉 크기 필드의 신뢰도(오프셋은 `MTBridge.swift`에 기록돼 있으나 **값 자체는 미검증**). 실기 확인 필요.

### B. 축소 — "볼륨만, 1손가락, 진입 판정"

A의 부분집합. 슬라이더 대상은 볼륨만, 손가락 1개 고정, 에지 슬라이더만. 제스처→액션은 그대로.
비용: 반나절~1일. 위험 낮음. **"기능 동결" 원칙과 가장 잘 맞는다.**

### C. 폐기 — 코드 제거, Ledge 안내

근거: 무료 경쟁 앱 다수, 카테고리 6~7위, 유지 비용(비공개 API·OS 업데이트 리스크) 상시.
비용: 제거·문서 정리. 위험: 기존 사용자(본인)의 사용 이력 손실. `docs/OPEN_ITEMS.md`에 "의도적으로 하지 않음"으로 기록.
주의: 비공개 프레임워크 의존은 **macOS 업데이트마다 깨질 수 있는 부채**다. 실제로 금지 심볼 1건이 macOS 27.2에서 SIGSEGV를 냈다(기존 실측).

### 비교

| | A 재설계 | B 축소 | C 폐기 |
|---|---|---|---|
| 사용자 체감 해결 | 높음 | 높음(볼륨 한정) | — |
| 비용 | 1~2일 | 0.5~1일 | 0.5일(제거·문서) |
| 유지 부채 | 유지 | 유지(감소) | **제거** |
| 제품 차별화 | 낮음~중간 | 낮음 | — |
| "기능 동결" 부합 | 낮음 | **중간** | **높음** |

## 7. 권고

1. **A 또는 B로 간다면 반드시 "2손가락 기본"을 버린다.** 이번 조사에서 가장 확실한 단일 원인이다. v0.33.1에서 감도만 12%→14%로 조정했지만 그 뒤에도 사용자는 기능을 껐다 — 스텝 모델을 유지한 채 파라미터만 만지는 것으로는 해결되지 않는다.
2. **C(폐기)도 정당한 선택이다.** 무료 전용 앱이 이미 더 잘하고, ApexKey의 제품 방향은 "신규 기능 동결 + 마찰 개선"이다. 다만 폐기 전에 **B를 반나절 써 보고** 판단하는 편이 후회가 적다.
3. 어느 쪽이든 **실기 확인은 사용자가 한다**(에이전트의 맥 제어 금지 지침 유지). 판정 기준은 하나로 충분하다: *"페이지를 스크롤하지 않고, 한 번의 손동작으로 볼륨 0→100%가 되는가."*
